# Local soldier listings and sales

Step 25 is VERIFIED for the local contract, checked API and wallet transaction flow, 10 November 2026. Full regression passed 359 application tests in 63 files, forty local chain integration checks across soldier sales, leases, soldiers, asset compatibility and existing weapon catalogs, and the strict production build. JourneySoldierMarket is a separate fixed price exchange for the existing JourneySoldiers collection and an explicitly registered local mock currency. It has its own ABI and deployment manifest. J10 authorized mint remains free and separate from trading. Sellers choose asking prices. The proof uses six mock units as an authored seller choice, not a suggested valuation, mint price, public price or promised return.

Listings bind the collection and token through the exchange call, plus seller, price, increasing listing nonce, progress revision, progress nonce and immutable build. Creating a listing requires the current owner and reviewed progress terms. Every purchase repeats the expected seller, price, listing nonce, progress revision and progress nonce. A different price, same price relisting, cancellation, progress update, lease, transfer or transfer followed by return makes an old quote unusable. Progress updates invalidate the quote without silently choosing a new asking price. Raw invalidated listing records can remain for inspection; the checked quote rejects them.

The seller approves the exact NFT to the market. The buyer uses exact ERC20 allowance, resetting a differing nonzero allowance before approving the asking price. Settlement consumes the listing, pays the seller, verifies exact buyer and seller balance changes, rechecks the current ownership and progress terms after the currency call, and safely transfers the soldier. Rejected payment, underpayment and rejected NFT delivery revert all effects, including currency movement, listing consumption, NFT approval changes and progress nonce changes. The market holds no sale proceeds. OpenZeppelin SafeERC20 and ReentrancyGuard supply the existing safety patterns.

The collection transfer path enforces J11 leases, and the market additionally rejects listing or buying a leased soldier. Release does not revive a prelease quote because lease operations advance the collection progress nonce. Cosmetic XP, verified furthest checkpoint, class, build, original artwork and provenance survive a sale. Account achievements remain outside token metadata and are not reassigned. The proof uses authored signer progress; the actual bank journal bridge is still Step 29.

SoldierCollections optionally accepts a separate local market manifest. It checks chain, collection, market code hash, mock currency code hash, immutable collection and currency addresses, and the fixed price policy. Soldier reads stay available without a market configuration, with listing capability false. A configured but unverifiable market fails its checks. JourneyAssetCatalog chooses the soldier adapter explicitly and preserves existing gun quote types and routes. Read only API `/weapons/journey-quote` accepts exactly kind=soldier, chainId=31337, collection and tokenId under the existing request limits. Queries with extra fields fail identity decoding. No browser request can register a market or change its currency.

SoldierMarketController provides refresh, review, list, cancel and purchase flows. Its states include awaiting wallet, pending, confirmed, rejected, replaced, stale, failed and refresh required. It rechecks quote terms before approval and before purchase and does not continue spending after rejection, replacement or staleness. A failed ownership refresh after confirmation retains the confirmed transaction hash. SoldierMarketWallet rechecks the connected account, network, code and exchange identity before signing, and reads each token or quote from one pinned block. It retains replacement scanning from the block before submission because wrapping a signer response as a contract response otherwise lost that scan boundary in the installed ethers implementation.

This shared wallet flow is implemented and tested against actual disposable contracts. It is not yet mounted as a soldier panel in the public Armory. Complete unified Armory presentation and human wallet interaction remain later gates. Owned Journey combat remains disabled; a transferable collectible does not establish combat admission.

Actual pending transactions are replaced at the same nonce with automining disabled: one is repriced and the other cancelled. Both stop the wallet flow without buying the soldier. Separate controller fixtures exercise wallet rejection, stale terms during approval, concurrent actions and failed refresh after a confirmed purchase.

The reproducible proof uses port 18583 and records thirteen successful local receipts. Wallet A lists a progressed soldier through the wallet controller. Wallet B reviews its verified history, resets a stale allowance, approves the exact price and buys once. Both wallet clients read B as the new owner, token history and URI remain identical, balances change by the exact price and the final allowance is zero. Evidence is in evidence/journey-soldier-market-proof.json and evidence/journey-soldier-market-local-deployment.json. These are closed disposable deployments.
